Working rules

Twenty-two rules for AI systems in production, from appendix A of The Forward Deployed Engineer's Handbook, put in plain words. Each is set against the alternative it beats. That alternative is not a mistake to laugh at: it is usually what a capable engineer would choose under pressure, which is why it needs answering. The handbook says these rules recur across the training and assessment programmes of many vendors, each in its own vocabulary, and that they will outlive the products that implement them [handbook ch. 2, appx A].

They are not a checklist. Most of them rest on five ideas, and the page is grouped by those [handbook ch. 24].

The examples come from the handbook's three running examples, which are fictional: a retailer's service agent that handles returns and refunds, an insurer's policy assistant and document pipeline, and a bank's programme of coding agents [handbook ch. 1]. They are not Fulfen Labs' clients, and the figures in them are the handbook's own. The numbers below are the handbook's, so you can look each rule up.

Idea 1. Put what must hold where it cannot be argued with

Some rules must hold every time. Put them in code, permissions and data access, where the model's choices cannot reach them [handbook ch. 24].

1. If a rule must always hold, enforce it in code, permissions or gates, not in a prompt.

  • Instead of: writing the rule clearly in the instructions and trusting the model to follow it.
  • Why: instructions are followed most of the time, not every time. Long context can crowd them out, and text the model reads can talk it out of them. A limit, a prohibition or a required order of steps belongs in something that runs whatever the model decides.
  • Example: the retailer's refund limit sits in the agent's instructions. In testing, a customer persuades the agent that "the manager already approved" a larger refund. The fix is a refund gate in code, with the limit held in configuration the finance team owns; the instructions only explain the process to customers [handbook ch. 21].
  • Chapters: 17, 21.

2. Limit what an agent can do by removing permissions, not by watching for misuse.

  • Instead of: granting broad access, then logging and alerting on anything unusual.
  • Why: monitoring tells you after the event, noisy alerts get turned down, and a manipulated agent acts at machine speed. What an agent cannot do, it cannot be tricked into doing.
  • Example: if the agent should never delete records, remove the permission. If it should never change a customer's address, do not give it the tool. A refund tool that can also cancel orders is two tools pretending to be one [handbook ch. 20].
  • Chapters: 20.

5. Decide who may see what at the data, never by telling the model.

  • Instead of: telling the model which documents this user may see and asking it not to reveal the rest.
  • Why: the instruction may not be followed, injected text can override it, and once restricted content is in the model's context it can leak through a summary, a citation or the model's reasoning. Content a user may not see must never reach the model on that user's behalf.
  • Example: a broker using the insurer's assistant is shown a passage from a document restricted to an underwriting team in another region, because the system ranked documents by relevance and asked the model to respect access. The fix is retrieval that runs as the user and filters by access policy before ranking, so the restricted document is never a candidate [handbook ch. 12].
  • Chapters: 12, 20.

9. A valid schema proves the shape of an answer, not that it is right; check the meaning too.

  • Instead of: assuming that strict output mode means the output is correct.
  • Why: the decoder enforces shape, not truth. A perfectly valid object can hold an invented date, a misread currency or totals that do not add up. Anything another system will act on needs checks of meaning in code, and a set route for what fails them: retry with feedback, fall back, or flag for a person, never a silent correction.
  • Example: an extracted invoice is valid output with the wrong totals. Checks in code catch it: each line's quantity times price, line items summing to the net total, net plus tax equalling gross. Sending the errors back to the model can fix a misread row; it cannot fix a total that only exists in an image the model never saw, and a model pressed to pass the check may invent one [handbook ch. 10].
  • Chapters: 10.

10. Make every write safe to repeat before turning on retries.

  • Instead of: retrying only on failure, on the grounds that duplicates will be rare.
  • Why: the most dangerous failure is a write that succeeded but whose reply was lost. To the caller it looks exactly like a failure. Without a write that is safe to repeat, every retry after a lost reply is a second payment, a second email or a second order.
  • Example: an agent changes a purchase order's approved quantity. The database commits; the reply is lost. If the retry carries a new request identifier, one intended change becomes two [handbook ch. 14].
  • Chapters: 14.

Idea 2. Assume the model will sometimes be wrong or fooled, and design for it

The handbook's revised edition (November 2026) finds that no current model reliably resists being misled, so the useful design question is not "how do we stop it being fooled?" but "what can a fooled model do?" [handbook ch. 20, 24].

4. Treat retrieved documents and tool results as untrusted input.

  • Instead of: trusting them because they came from your own systems.
  • Why: anything an outsider can influence can carry instructions: a customer message, a supplier invoice, a shared document, a web page, another agent's output. The model cannot reliably tell an instruction from data. Keep such content in the data, mark where it came from, and make sure acting on it needs authority the content cannot grant.
  • Example: in the retailer's system, every customer message is untrusted. In the insurer's, every document in the library is untrusted, even those written by its own staff, because anyone who can edit a document can try to instruct the agent [handbook ch. 20].
  • Chapters: 20.

6. When answers are confidently wrong, look at retrieval before the model.

  • Instead of: blaming hallucination and changing to a better model.
  • Why: in a grounded system, most fluent wrong answers come from wrong, stale or missing evidence. A stronger model given the same evidence is wrong more persuasively. Changing the model cannot repair a missing table row.
  • Example: a broker asks the insurer's assistant a policy question and gets a fluent answer, with a cited clause and a sublimit. Three things are wrong: the clause is last year's superseded wording, the sublimit was read from the wrong row of a table whose header was lost across a page break, and the cited passage came from a document the broker should never have seen. The model did its job; every failure happened before it saw a word [handbook ch. 12].
  • Chapters: 12, 19.

8. Decide in advance what happens when there is no good answer, and when a person takes over.

  • Instead of: expecting the model to say when it does not know, or to escalate when it is unsure.
  • Why: models trained to be helpful lean towards answering, and a model's own confidence is a poor guide to whether it is right. Saying "I can't find that" is a designed behaviour, with criteria, wording and tests. Hand-offs to a person follow conditions you can define and test, not mood or self-reported confidence.
  • Example: an angry customer may have a simple request, and a calm one may be asking for something outside policy; escalating on tone gets both wrong. For abstention, the handbook advises a test set of questions the documents cannot answer, measuring both how often the system answers when it should abstain and how often it abstains when the answer is there [handbook ch. 12, 16].
  • Chapters: 12, 16, 21.

20. Have someone other than the author check the work.

  • Instead of: asking the author, person or agent, to check its own work before submitting it.
  • Why: an author shares its own blind spots. The misunderstanding that produced the bug also persuades it the code is correct. A separate reviewer, deterministic checks and a person, each independent of the author, catch what self-review cannot.
  • Example: where an agent reviews a coding agent's change, it is a separate instance with its own instructions and no sight of the author's reasoning, so it judges the change on its merits. In the published code migrations the handbook cites, ordinary human code review was kept for every agent change as well [handbook ch. 17].
  • Chapters: 17.

Idea 3. Spend scarce resources deliberately

Context, tools, memory, money and time are all limited. Spend each on purpose [handbook ch. 24].

7. Treat context as a budget: more of it is not automatically better.

  • Instead of: giving the model everything that might be relevant, because the window is large.
  • Why: the research the handbook cites (revised edition, November 2026) finds that quality falls as the window fills, and falls further for content buried in the middle. Every extra token costs money on every call, and irrelevant material actively distracts. Each item in the window should earn its place on this turn.
  • Example: twenty turns into a conversation about three problems at once, the retailer's agent offers the wrong refund amount. The right figure appeared once, in a tool result on turn four, and was lost among everything since. Nothing crashed; the one fact that mattered had become easy to miss [handbook ch. 11].
  • Chapters: 11.

12. Give an agent fewer, sharper tools, clearly described, and reveal more only when needed.

  • Instead of: exposing every operation, or connecting every approved service, so the agent can do anything.
  • Why: every tool's description takes up context on every turn, every extra tool is another choice the model can get wrong, and every connected service widens what an injected instruction can reach. Give a task the smallest set it needs, and an index from which to load the rest on demand.
  • Example: two tools called "search" and "find" that overlap invite the wrong choice. Merge them, or make each description say exactly where one ends and the other begins [handbook ch. 14].
  • Chapters: 14, 15.

13. Choose the kind of memory to fit what needs remembering.

  • Instead of: storing the whole conversation and replaying it.
  • Why: a replayed transcript grows without limit, brings back stale and superseded content, and makes the agent search its own history for the one fact it needs. For each kind of information, decide how long it must live, who may read it and how it will be found again; then choose session state, a structured record or searchable memory.
  • Example: the retailer wants the agent to remember that a customer prefers email to phone. That is one durable, structured entry, with where it came from and what it replaced, retrieved when contact preferences matter, not a replay of every past conversation [handbook ch. 11].
  • Chapters: 11.

18. Make cost and latency release gates; cache, batch and route before moving to a bigger model.

  • Instead of: getting quality right first and dealing with cost later.
  • Why: cost and latency are properties of the design, not settings to tune afterwards. A design that needs many model calls per request will not become cheap later, and a slow user-facing path will not be used. Set cost and latency budgets alongside quality targets at the start, and gate releases on all three. Measure cost per successful outcome, not per call: a cheaper model that fails more often can cost more.
  • Example: the handbook's own illustration is a design that needs eight model calls per request, and a user-facing path that takes twenty seconds. Neither becomes acceptable by tuning later [handbook ch. 19].
  • Chapters: 19.

Idea 4. Earn autonomy and change on evidence

Autonomy and change are granted step by step, each step on evidence that the last one worked [handbook ch. 24].

3. Give a task only the autonomy it has earned; a fixed workflow or a plain function is often better.

  • Instead of: using an agent because it can handle the unexpected.
  • Why: an agent's flexibility is also its unpredictability. If the unexpected cases can be listed, or an unexpected action would be costly, a workflow or a plain function is cheaper, easier to test and easier to explain. Start at the lowest level that solves the problem and move up only when that level is shown to fail.
  • Example: the insurer clearing a backlog of disputed invoices, one agent per invoice, looks like a team of agents. It is a workflow: the invoices do not affect each other, so nothing needs agents to reason together [handbook ch. 16].
  • Chapters: 9, 13, 16.

16. Use deterministic checks first, and a calibrated model judge only for what they cannot check.

  • Instead of: using a strong model as judge for everything, because it is flexible and scales.
  • Why: a judge is itself a probabilistic system with known biases. Using one where code could have checked adds cost and noise to something that could have been certain. Use a judge for the rest, and only once you know how often it agrees with a person.
  • Example: "exactly one refund exists for this operation identifier" is a check in code against the system of record. "Is this answer supported by its sources?" is a question for a judge, checked against people's verdicts [handbook ch. 18].
  • Chapters: 18.

17. Before a falling score blocks a release, tell real regression from ordinary variation.

  • Instead of: blocking the change whenever the score goes down.
  • Why: evaluation scores carry sampling error and vary from run to run. A gate that reacts to noise blocks good changes and teaches the team to ignore the gate. Compare old and new on the same cases, state the uncertainty, and look at which cases moved from pass to fail.
  • Example: run the unchanged system several times first, to see how much its score moves on its own, before blaming a change for a two-point drop [handbook ch. 18].
  • Chapters: 18.

21. Keep planning apart from approved execution.

  • Instead of: letting the agent work directly and reviewing the result.
  • Why: on any change large enough that the result is harder to review than the intent, a wrong approach found in a plan costs minutes. Found in a two-thousand-line change, it costs hours, and is often accepted because nobody wants to throw the work away.
  • Example: an engineer asks an agent to change a shared interface used by nine services. The agent first writes a plan (the files, the approach, the tests, the risks) without changing anything; a person approves it; then the agent works within it [handbook ch. 17].
  • Chapters: 17.

Idea 5. Keep the system explicable and changeable

Someone other than the builder will have to understand, audit and change the system. Make that possible from the start [handbook ch. 24].

11. Return structured errors, and tell an empty result apart from a failure.

  • Instead of: raising an exception, or returning a message, and leaving the model to work it out.
  • Why: without being told, the model cannot tell a passing timeout from a policy refusal from an outcome nobody is sure of, and each needs a different response. Treating an uncertain outcome as a failure is how a refund gets paid three times.
  • Example: "Refund declined: this order was already refunded on 3 October (refund R-4471). Do not retry; tell the customer the refund was issued." That is an error an agent can act on correctly, and a person reading the trace can follow [handbook ch. 14].
  • Chapters: 14.

14. A subagent knows only what it is given, so brief it explicitly and in a fixed structure.

  • Instead of: trusting the subagent to work it out from its instructions, or passing it the whole conversation.
  • Why: both fail. A missing constraint becomes a wrong decision. A subagent given everything inherits all the coordinator's clutter, at many times the cost. Give each one a structured brief with exactly what its task needs.
  • Example: if the coordinating agent has decided a refund goes back to the original payment method, every subagent that touches the refund must be told, or one of them will decide otherwise [handbook ch. 16].
  • Chapters: 16.

15. Keep track of where data came from through every step that changes it.

  • Instead of: keeping the source for original documents and treating derived data as if it stood alone.
  • Why: every chunk, extraction, summary and cached answer is a transformation. The moment one loses its source, nobody can audit it, correct it or say which revision it reflects.
  • Example: the insurer's auditors need to know where every answer came from. So every claim in an answer cites the passage it came from, with its source, location and revision, generated from what was actually retrieved, not from the model's memory [handbook ch. 12, 21].
  • Chapters: 12, 21.

19. Defend each choice against the option you nearly chose; start with a capable option and optimise down.

  • Instead of: defending a design on its own merits, or picking the cheapest model that seems to work.
  • Why: almost every design has merits, and a reviewer arrives with the nearest alternative already in mind. Reviewers trust a design whose author has named that option and the constraint that defeats it. For models, start capable to learn what quality is possible, then move to smaller or cheaper ones only as far as your evaluations allow; starting cheap hides whether failures come from the model or the design.
  • Example: "A single agent with tools rather than three cooperating agents, because the work shares one context and parallelism saves nothing measurable." One sentence like that per major choice is the core of the design document [handbook ch. 9].
  • Chapters: 9, 10, 24.

22. Version prompts, configuration and model pins, and release them like code.

  • Instead of: treating prompts and settings as content that people edit in place.
  • Why: each changes behaviour as much as a code change does. If they change outside the release process, nobody can say which combination was running when the system last worked, test a change before it ships, or roll back. A release is the complete set: code, instructions, tool descriptions, configuration, model identifiers and retrieval settings, versioned together.
  • Example: three months after launch, the retailer's agent has become "a bit off". The prompt sits in a table two teams can edit, the model name now points to a newer version, and a setting switched on for a demo was never switched off. Nobody can roll back, because there is nothing to roll back to [handbook ch. 22].
  • Chapters: 22.

One more, still a candidate

The handbook names a further rule that is well supported but not yet stated as widely as the twenty-two [handbook appx A].

Make the work checkable before you make it autonomous.

  • Instead of: deploying the agents and fixing the codebase as problems appear.
  • Why: agent output is only as trustworthy as it is checkable. A codebase without fast, reliable automated checks hands every check to human reviewers, who become first the bottleneck and then the point of failure. Readiness comes before autonomy, and is often the first piece of work.
  • Example: the bank's head of engineering asks why a programme about coding agents has started by adding tests and type checks to the codebase. This is why [handbook ch. 2, 17].
  • Chapters: 17.
